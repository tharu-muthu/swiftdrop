# SwiftDrop shared rules

- Read relevant `docs/reference/` files and `docs/reference-review.md` before changes. Preserve references. The assignment defines requirements; v3 and the user's agreed decisions define this implementation baseline. Record conflicts instead of guessing.
- One React frontend, one Java 21 / Spring Boot 3.5.16 application, one PostgreSQL database and shared `swiftdrop` schema per environment. Developers may use separate Neon development branches with the same schema/migrations. RabbitMQ handles asynchronous integrations. No microservices or per-feature databases/schemas.
- Request direction: React -> Controller -> Service -> Repository -> PostgreSQL. Java packages are `com.swiftdrop.<layer>.<feature>`; frontend features live in `src/features/<feature>`.
- Controllers validate DTOs and call services, never repositories. Services own business rules, resource authorization and transactions. Repositories own persistence. Never expose entities as API responses. Use constructor injection and `jakarta.validation`.
- Features: M1 identity; M2 merchant; M3 pricing; M4 booking; M5 dispatch; M6 execution; M7 tracking; M8 notification; M9 webhook. Call other features through service contracts, not their repositories or internal HTTP.
- APIs use `/api/v1`. GET health stays public. Keep unimplemented routes denied; expose auth/OIDC entry points only with their implementation and security tests. No generated demo login, fake production principals or broad `permitAll`. Preserve CSRF on cookie-authenticated operations.
- M1's plan and acceptance criteria are in `docs/identity/implementation-checklist.md`. Roles are exactly `CUSTOMER`, `MERCHANT`, `COURIER`, `DISPATCHER_ADMIN`; public signup creates CUSTOMER only. M2 owns merchant approval/access, M5 owns courier operational profiles, and each module enforces ownership of its records. Share identity through trusted `IdentityContext` and service contracts, not client-supplied IDs/roles or cross-feature repositories.
- Implement identity with access JWTs held in React memory, hashed rotating refresh tokens in persistent sessions, and protected HttpOnly refresh cookies. Check account/session/authorization state on protected requests so logout, suspension and role changes take effect immediately. Never disable CSRF globally or trust stale role claims.
- Google identities use verified provider/subject; matching email alone never links accounts. Recovery must use expiring single-use hashed tokens, generic responses and session revocation. Keep provider secrets and reset delivery on the backend. Review proposed schema/API/policy choices in the checklist before implementing them.
- Flyway is the only schema writer; JPA uses `ddl-auto: validate`. Coordinate the single migration sequence; never edit an applied migration. Use PostgreSQL integration tests. Keep demo fixtures separate.
- Future domain data uses UUIDs, UTC timestamps, integer grams and LKR minor units. M6 owns canonical parcel status. Plan outbox persistence, independent durable queues and idempotent consumers when event features are implemented.
- Pin direct npm dependencies and commit `package-lock.json`; install with `npm ci`. Use the Maven wrapper; let the Spring Boot parent manage Spring dependency versions. Coordinate toolchain changes with the team.
- Never commit secrets, `.env`, tokens or personal data. Never put secrets in `VITE_*` variables. Return safe errors and avoid sensitive logging.
- Neon credentials belong in private `backend/.env`: `SPRING_DATASOURCE_URL`, `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD`. Runtime uses that connection; Flyway uses a direct connection to the same endpoint/database, derived by `DatabaseMigrationConfig` or explicitly configured with `SPRING_FLYWAY_URL/USER/PASSWORD`. Preserve the destination guard and test overrides for both connections. Vite reads only frontend configuration. Use the documented Maven launch so `.env` paths resolve consistently.
- Registration accepts only `fullName`, `email`, `password`; reject other fields. Confirmation stays in React memory. Always assign CUSTOMER server-side in one transaction and let DB uniqueness resolve races. Normalize email through the existing database rule; never normalize passwords. Apply the documented 8–128 Unicode code-point policy and adaptive encoder. Preserve CSRF, safe errors and credential-log suppression; no automatic sign-in. See `contracts/identity-registration.md`.
- Use small feature branches and peer review. Add meaningful tests for behavior/security changes. Run frontend tests/build and backend verification; run integration tests with Docker. Report passed, failed and unrun checks separately. Exact commands are in `README.md`.
- M1 database foundation is V2 plus validated JPA mappings; current ER/invariants are in `docs/identity/schema.md`. Preserve generated normalized-email uniqueness, UUID role IDs, hashed token columns, stable sessions/rotation history and append-only audit. Do not seed accounts/passwords. IAM-01 now reuses these tables; later IAM stories and other modules remain separate tasks.

- IAM-02/IAM-07 use Spring Security/Nimbus HS256, configurable issuer/audience/lifetimes and a private AUTH_JWT_SECRET. Follow `docs/identity/sessions.md` and `contracts/identity-sessions.md`. API contexts are request-only; preserve the separate future OAuth session chain. Lock user then session for refresh/logout; commit family revocation before returning reuse errors. Check current DB state/roles for every protected request.
- Browser auth lives in memory. Coordinate refresh with one promise and cross-tab Web Locks, retry a 401 only once, never refresh on 403, and never retry an ambiguous refresh failure. Preserve origin/CSRF checks and Secure cookies except explicit loopback development.
