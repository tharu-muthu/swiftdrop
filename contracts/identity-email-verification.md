# Email ownership verification

New password registrations create an unverified CUSTOMER account and return the existing safe `201` account response. After commit, the backend queues an email with a single-use verification link. The frontend displays **Check your email**. Password login and protected requests require `email_verified_at` to be set. A correct password for an active unverified account returns `403 EMAIL_VERIFICATION_REQUIRED`; unknown accounts, wrong passwords and suspended accounts still receive the same generic `401 INVALID_CREDENTIALS` response.

Docker captures verification messages in Mailpit at `http://localhost:8025` by default. To deliver them to real inboxes, set the private Gmail SMTP values described in [password recovery](identity-password-recovery.md) in `backend/.env`; the same sender delivers both verification and password-reset messages. `MAIL_FROM` must match `SPRING_MAIL_USERNAME`. The standard Gmail App Password contains 16 characters without spaces. The Compose configuration uses private `SPRING_MAIL_*` values in preference to its Mailpit host and port. Keep these values out of Git and the frontend.

`POST /api/v1/auth/email-verification/request` accepts `{ "email": "person@example.com" }` and returns the same `202` acknowledgement for unknown, already verified, suspended, Google-only and eligible accounts. It is the resend path for people who registered previously. `POST /api/v1/auth/email-verification/confirm` accepts `{ "token": "..." }` and returns `204` after successful verification or `400 INVALID_VERIFICATION_TOKEN` for missing, used, revoked or expired links. Both endpoints use the existing CSRF and origin checks, `Cache-Control: no-store`, and rate limits.

Flyway V9 adds nullable `users.email_verified_at` and `email_verification_tokens` with UUID IDs, FK, hashed-token uniqueness and a partial unique index for one outstanding link per user. Existing Google-linked users are backfilled as verified because the OAuth callback required a verified email claim. Existing password accounts remain unverified: no previous inbox proof exists. They need a verification link before another login or protected request. The migration preserves all users, passwords and sessions; successful verification increments authorization version and revokes earlier sessions so stale access cannot revive. Password reset confirmation also establishes inbox ownership. Google-only accounts continue through Google and matching email alone never links accounts.

Links are built from private `RESET_FRONTEND_ORIGIN`, not the request Host. The raw token exists only in the email URL fragment and is removed from browser history before confirmation; PostgreSQL stores its SHA-256 hash. Links expire in 24 hours. Delivery uses the backend SMTP adapter on the bounded identity mail executor after commit. Failures are logged without addresses or tokens; users can request another link. The generic `202` response is not delivery confirmation.

**Deployment gate:** do not run this branch's Docker build/start against a shared Neon branch until real SMTP delivery has been tested with a password account and the team is ready for existing password accounts to verify. Test against isolated PostgreSQL with `./mvnw -Pintegration -Dit.test=RegistrationIT,IdentitySessionsIT verify` from `backend/` (Windows: `./mvnw.cmd`). Coordinate V9 with the migration owner immediately before merging; renumber this unapplied migration if another V9 lands first. Do not edit an applied migration.
